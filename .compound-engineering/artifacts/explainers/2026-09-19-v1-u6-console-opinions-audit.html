Юнит не учит worker писать opinions — это уже V1-U5. Здесь ты открываешь карточку оператору: API отдаёт то, что уже лежит в колонках, плюс читаемый audit; фронт перестаёт жить на MVP-поле rationale.

Два источника, один экран: opinions едут в списке кейсов (poll каждые 2с), audit — отдельным GET только для выбранного кейса.

1. Почему убрали rationale с консоли

В MVP на карточке было одно nullable-поле rationale — «why» от опциональной модели. В v1 на кейсе уже две колонки (dispatcher_opinion, critic_opinion), а rationale с V1-U3 никто не заполняет. V1-U6 рвёт контракт консоли: DTO больше не врёт, что живой текст — это rationale.

Колонку в Postgres не дропают (KTD3: один цикл миграций). Dual-write запрещён — старые строки в rationale на карточке не всплывут. Это осознанно.

2. Audit: писали давно, читать начали сейчас

Approve/reject и model/tool вызовы уже клали строки в audit_entries. Не хватало чтения: GET /cases/{id}/audit → массив {id, actor, action, why, created_at}, oldest first (KTD6).

404, если кейса нет — иначе пустой массив до первого действия. После approve в тесте появляется ровно одна строка оператора (demo-operator / approve).

3. Orval — почему «схема → dump → gen» в том же юните

Pydantic / routes → make openapi → openapi.json → pnpm gen:api → hooks + models

ADR 0007: консоль не копирует пути руками. Как только CaseListItem и audit route меняются, без dump фронт остаётся на старых типах с rationale и падает на типах или в runtime.

Мелочь типов: у audit path-параметр, поэтому orval кладёт в union и 422. В App.tsx audit берётся только при status === 200 — иначе TypeScript не сужает data до массива.

4. Карточка: rule-only vs два голоса

Правило открыло кейс без модели → оба opinion null → один fallback: «Rule opened the case. No model proposal.» Кнопки Send/Dismiss всё равно на open (ADR 0002 / KTD9): «уверенный» proposal — это оба opinion non-null после fenced persist, не статус job.

Как только хотя бы один текст есть — два блока Dispatcher / Critic (пустой слот показывает «—»).

5. Poll: три потока, не один

Как и раньше: cases и events каждые 2с. Новое: audit того же интервала только пока выбран кейс (enabled: selectedId != null). После decide инвалидируются и cases, и audit — иначе операторская строка появилась бы только на следующем тике poll.

Что юнит сознательно не делает

  • Не трогает worker / StateGraph / запись opinions.
  • Не дропает колонку rationale.
  • Не показывает kind на ленте как chip (отложено в плане).
  • Не добавляет Compose worker — это V1-U7.

Как проверить у себя

  • make test-api — opinions в list, audit после approve, 404.
  • pnpm test в apps/web — кнопки + empty copy + два лейбла.
  • Вручную: без key — fallback и пустой audit; approve — строка оператора; с worker+key — два блока opinion и tool/model rows.
